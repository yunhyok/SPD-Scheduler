# SPD Scheduler

<img src="assets/icon.png" width="112" alt="Circuit board and clock icon">

Windows 트레이에서 PowerSI SPD 파일의 순차 실행과 예약 실행을 관리합니다. C# WinForms / .NET 10, Windows 10·11 x64를 대상으로 합니다.

**현재 버전: v0.1.7.** 설치·업데이트 관리를 위해 [정식 GitHub Release](https://github.com/yunhyok/SPD-Scheduler/releases/latest)로 제공합니다. 실제 PowerSI 2025.1 GUI 연동의 전체 실측 검증은 남아 있습니다. `-tcl` GUI 실행, 각 저장 모드의 시작·완료·저장·종료는 별도 허용 PC에서 [검증 절차](docs/VALIDATION.md)에 따라 확인해야 합니다.

## 사용법

1. 설치 후 시작 메뉴에서 SPD Scheduler를 엽니다. 평소에는 트레이에 있으며, 아이콘을 더블클릭하면 목록이 열립니다. 창의 X는 숨기기입니다. 앱 종료는 트레이 메뉴의 **종료**를 사용합니다.
2. **설정**에서 PowerSI 실행 경로를 확인하고 변경했다면 **저장**합니다. 경로가 비어 있으면 **시작** 시 설치된 PowerSI를 자동 탐색해 실제 설정에 저장합니다. 탐색에 실패하거나 지정 경로가 잘못되면 예약 진행을 활성화하지 않고 안내합니다. 시뮬레이션 설정은 SPD에 미리 저장되어 있어야 합니다.
3. SPD 파일을 목록에 드롭하거나 **파일 추가**로 선택합니다. 드롭으로 전달된 순서가 유지됩니다. 긴 파일명은 좌우로 자동 이동하며, 툴팁과 우클릭 **전체 경로 복사**로 전체 경로를 볼 수 있습니다.
4. 필요한 행에 **예약**을 설정하고 **시작**을 누릅니다. 예약 시간이 지난 작업이 먼저 실행되며, 같은 예약 시간이면 등록 순서입니다. 미래 예약은 일반 대기 작업을 막지 않습니다.
5. **일시 중지**는 다음 작업 시작만 막습니다. 현재 시뮬레이션의 완료 확인·저장·정리는 계속됩니다.

확인 간격은 기본 **1분**이며 설정에서 **1~60분**으로 변경할 수 있습니다. **시작**을 누르면 즉시 첫 확인을 수행합니다. **지금 확인**은 같은 안전 조건으로 한 번 더 확인하며 강제 실행이 아닙니다. 하단에는 마지막 확인 시각, 다음 확인 예정 시각 또는 확인 중 상태를 표시합니다. 예약 도래 및 시뮬레이션 완료는 다음 확인 시점에 처리합니다. 업데이트할 때는 트레이 메뉴에서 스케줄러만 종료한 뒤 새 설치파일을 실행하세요. 진행 중인 PowerSI와 기존 큐는 유지됩니다.

앱 재시작 시 큐는 복구되지만 자동 진행은 일시정지됩니다. 기존 실행이 있으면 먼저 연결하여 확인합니다. `확인 필요` 항목은 PowerSI를 직접 확인한 후 관련 프로세스의 종료가 확인되어야 재시도하거나 건너뛸 수 있습니다. 외부 PowerSI는 저장하거나 종료하지 않습니다.

자동 판정이 복구되지 않으면 PowerSI에서 시뮬레이션 완료와 결과 저장을 직접 확인한 뒤, 해당 행을 우클릭해 **수동 완료 처리…**를 선택할 수 있습니다. `확인 필요` 또는 `실패` 항목을 **완료 (수동)**로 기록하며 기존 오류와 실행 기록을 보존합니다. `확인 필요` 항목은 **제거**, 우클릭 **제거 (Delete)** 또는 Delete 키로 확인 창을 거쳐 목록에서 제거할 수도 있습니다. 원본 SPD와 실행 로그는 지우지 않습니다. 이 동작들은 PowerSI에 저장·종료 명령을 보내지 않고 해당 항목의 자동 관리를 끝내며, 후속 큐는 **시작**을 누를 때까지 일시정지합니다. 다시 시작하면 외부 PowerSI 상태를 평소처럼 확인합니다. 실제 시작·실행·저장 중인 항목에는 수동 정리를 적용하지 않습니다.

v0.1.6은 자체 실행의 프로세스 조회 실패로 완료 검사가 막히던 경로를 수정합니다. **프로세스 확인 재시도 대기** 중에는 PID·실행 파일명·실패 단계를 표시하며 다음 확인에서 다시 조회합니다. 일시적인 조회 실패만으로 자동 진행을 끄지 않고, 해당 작업과 후속 작업을 유지합니다. 이전 버전에서 `확인 필요`로 보류된 작업은 PowerSI를 열어 둔 채 스케줄러만 업데이트한 다음 **지금 확인**을 누르세요. 저장·종료 후 `완료`로 바뀌면 **시작**으로 후속 큐를 활성화합니다. 시작 전이를 관측한 기록이 없으면 완료 문구만으로 자동 저장하지 않습니다.

예약 실행 직전에도 PowerSI 경로를 다시 검사합니다. 실행 파일이 사라지거나 접근할 수 없으면 큐를 일시정지하고 대기 작업·예약을 보존합니다. 이미 실패한 항목은 자동으로 다시 실행하지 않습니다. **실패 상태를 더블클릭**하거나 행을 우클릭해 **작업 상세**를 열면 오류·실행 ID·PID·시각·로그 위치를 복사할 수 있습니다. 원인을 해결한 뒤 **다시 대기**를 선택하고 필요한 예약을 설정한 다음 **시작**하세요. 지난 예약을 그대로 두면 다음 실행 가능한 확인 시점에 진행합니다.

예약은 입력한 로컬 날짜·시각의 UTC 오프셋 및 시간대 ID를 보존하는 일회성 예약입니다. 이후 Windows 시간대를 바꾸어도 실행할 절대 시각은 바뀌지 않습니다. 절전에서 복귀하면 지난 예약을 다시 확인합니다. PC 자동 켜기 및 Windows 서비스는 포함하지 않습니다.

## 상태 판정

- **자체 실행:** 실행 ID별 Tcl 이벤트와 새 GUI 상태 전이 또는 작업별 로그 규칙으로 시작·완료를 확인합니다. `begin simulation` 반환은 완료가 아닙니다. 완료 승인 → 저장 성공 이벤트 → 해당 PowerSI 및 알려진 자식 프로세스 종료가 모두 확인되어야 다음 작업을 진행합니다.
- **외부 실행:** PID·시작 시각·실행 경로와 자식 프로세스를 설정한 분 단위 간격으로 관측합니다. 기본 저부하 조건은 60초 동안의 연속 관측, 단일 코어 환산 CPU 합계 50% 미만, 메모리 변화 합계 128 MiB 이하, 프로세스 읽기/쓰기 64 KiB/s 미만입니다. 아래 동시 진행 정책을 적용한 대상에 대해 **유휴 추정**으로 실행을 허용합니다. 설정 간격과 상태 읽기 소요 시간을 합한 값보다 10초 이상 늦어진 관측·프로세스 변경은 측정을 다시 시작합니다. 실제 시작 직전에도 다시 검사합니다.
- **외부 BbsCon 동시 진행:** 기본으로 허용하며 설정에서 끌 수 있습니다. 검증된 PowerSI와 같은 실행 폴더에 있는 자식 `BbsCon.exe` 및 그 콘솔 호스트의 CPU·메모리·I/O를 다음 작업의 차단 조건에서 제외합니다. 이미 확인한 같은 프로세스는 부모 종료 후에도 식별합니다. BbsCon을 저장·종료하거나 완료로 표시하지 않습니다. 다른 solver, 새 PowerSI, 실행 중·일시정지·라이선스 대기 신호는 계속 확인합니다. 스케줄러가 직접 실행한 작업의 저장·자식 정리 조건은 유지합니다.
- **완료된 외부 GUI의 I/O:** 같은 PowerSI가 연속 두 관측에서 `Simulation Done.`을 표시하면 그 창의 I/O를 차단 조건에서 제외합니다. 해당 창의 CPU·메모리와 다른 자식 solver는 계속 검사합니다. 완료 문구가 사라지거나 실행 중 신호가 보이면 다시 일반 조건을 적용합니다.
- 같은 PowerSI의 실행 중 → 완료 전이를 직접 관측하고, 모든 PowerSI 창에서 이 전이가 확인되며 동시 진행 정책 적용 후 저부하가 한 확인 간격 유지되면 긴 사용자 지정 유휴 시간을 단축할 수 있습니다. 처음부터 보이던 완료 문구나 알 수 없는 상태에는 이 경로를 사용하지 않습니다. 자체 실행의 저장·종료 승인 기준은 유지합니다.
- 읽을 수 있는 상태 표시줄의 실행·일시정지·라이선스 대기 신호는 저부하 추정보다 우선합니다. LLM과 화면 인식은 사용하지 않습니다. PowerSI UI 접근은 전용 console-subsystem 보조 EXE에 시간 제한을 두며, 창 없이 실행하고 응답 없는 보조 프로세스만 종료합니다. GUI 스케줄러를 상태 확인 때마다 재실행하지 않습니다.
- 모드별 로그 규칙은 설정에서 입력합니다. **작업 이름 / SPD 한 줄 식별 정규식 / 시작 정규식 / 완료 정규식**이 모두 필요합니다. 정확히 하나의 SPD 규칙만 일치해야 적용합니다. 기본은 대소문자를 구분하며 `(?i)`로 무시할 수 있습니다. 검증되지 않은 기본 완료 규칙은 배포하지 않습니다. `AFS Finished`를 모든 모드에 적용하지 마세요.

하단 CPU 표시는 **전체 PC의 논리 프로세서 기준**이며, 설정의 **CPU 한도 (1코어 %)**는 단일 코어 합계 기준입니다. 예를 들어 논리 프로세서 64개에서 단일 코어 100%는 전체 PC의 약 1.56%입니다. **감시 상세**에는 전체 관측값과 실제 판정에 사용한 값, 동시 진행으로 제외된 PID와 이유를 구분해 표시합니다. 내용은 Ctrl+A, Ctrl+C로 복사할 수 있습니다. 작업 관리자의 현재 GUI 행과 달리 자식 프로세스까지 포함한 관측 구간 평균이므로 두 수치가 항상 같지는 않습니다.

I/O는 **프로세스 읽기/쓰기와 기타 I/O**로 나누며, 기타 I/O는 차단 조건에 사용하지 않습니다. 읽기/쓰기에도 파일 캐시·네트워크 등이 포함될 수 있어 작업 관리자의 물리 디스크 사용량과 같지 않습니다. Windows 카운터의 의미는 [Microsoft IO_COUNTERS 문서](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-io_counters)를 참고하세요. 기존 I/O 한도 값은 읽기/쓰기 한도로 유지합니다.

부모 PID만 같은 오래된 프로세스는 자식으로 간주하지 않도록 생성 시각을 검증합니다. 이미 확인한 살아 있는 solver 자식은 부모 종료 후에도 감시합니다. 여러 창이 열린 것 자체는 실행 차단 조건이 아닙니다. BbsCon 동시 진행을 끄면 BbsCon도 일반 리소스 조건으로 검사합니다.

자체 실행에 기록된 PID는 같은 Windows 프로세스 핸들에서 종료 여부·생성 시각·이미지 경로를 확인합니다. 생성 시각이 다르면 재사용된 PID이므로 이전 작업의 살아 있는 자식으로 취급하지 않습니다. 실행 파일 경로는 모듈 목록 대신 [QueryFullProcessImageName](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew)으로 조회합니다. 조회 실패 시 같은 핸들에서 종료를 재확인하며, 실제 접근 거부는 종료로 간주하지 않습니다.

v0.1.3부터 이전 기본 CPU 1%·메모리 16 MiB 조합을 처음 불러올 때 50%·128 MiB로 한 번 변경합니다. 이 조합에서 유휴 시간도 이전 기본 180초이면 60초로 변경합니다. 사용자 지정 값과 확인 간격은 유지하며, 이후 사용자가 엄격한 값으로 다시 설정하면 그대로 보존합니다. 1분 확인 간격은 **1분 이내 완료 인식 보장**이 아닙니다. 첫 기준점과 60초 저부하 구간이 필요하며, 완료 직후 이전 계산이 평균에 포함되거나 프로세스 구성이 바뀌면 한 번 더 확인해야 할 수 있습니다. 감시 상세에서 측정 시각·평균 구간·상태 읽기 결과를 확인하세요.

실행 거부가 명확한 경우에만 자체 PowerSI에 저장 없이 종료를 요청하고, 종료 확인 후 다음 파일로 진행합니다. 활동·관측 실패 등으로 시작 여부가 불명확하거나 저장·정리가 실패하면 자동 진행을 보류합니다. 기본 시작 확인 제한시간은 10분입니다.

## 데이터와 로그

`%LocalAppData%\SPDScheduler`에 `queue.json`, 이전 저장본 `queue.json.bak`, `logs`, `runs/<실행 ID>`를 보관합니다. 큐는 임시 파일 쓰기·디스크 flush·원자적 교체로 저장하며, 실행 ID는 프로세스 생성 전에 기록됩니다. 손상된 큐를 조용히 초기화하지 않습니다.

실행별 폴더에는 `events.log`, `output.log`, `runtime-errors.log`, `error.txt`, 생성된 `run.tcl`, 복구 및 제어 토큰이 저장됩니다. 행의 우클릭 **로그 폴더 열기**로 확인하세요. 파일 경로와 로그에 제품 정보가 포함될 수 있으므로 공개 이슈에는 원본을 올리지 마세요. 설치 제거 시 대기열·로그는 보존됩니다.

## 빌드와 테스트

필수 도구: Windows x64, [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0), [Inno Setup](https://jrsoftware.org/isinfo.php), Git. 별도 NuGet 테스트 프레임워크 없이 실행 가능한 콘솔 테스트를 사용합니다.

```powershell
dotnet build SPDScheduler.slnx -c Release
dotnet run --project tests/SPDScheduler.Tests -c Release --no-build
./tools/Build.ps1
```

`Build.ps1`은 테스트 후 런타임을 포함한 앱·상태 읽기 보조 EXE와 사용자 단위 설치파일을 만듭니다. 두 EXE는 각자 런타임을 포함하므로 설치 용량이 늘어납니다. `ISCC` 환경 변수 또는 PATH로 Inno Setup 컴파일러를 지정할 수 있습니다. 산출물은 `artifacts/installer`의 설치 EXE, SHA-256, `build-manifest.json`입니다. GitHub Actions도 같은 스크립트로 빌드하며 artifact를 제공합니다. CI에서 PowerSI를 실행하거나 정식 Release를 자동 게시하지 않습니다.

PowerSI가 차단된 UI 확인 방법:

```powershell
./artifacts/publish/SPDScheduler.exe --safe-mode --show
# 별도 임시 데이터 폴더를 지정하려면 --safe-mode와 함께 사용
./artifacts/publish/SPDScheduler.exe --safe-mode --show --data-dir "C:\Temp\SPD Scheduler UI"
```

안전 모드는 PowerSI 탐지·실행·제어 어댑터를 대체하고 별도 큐를 사용합니다. 일반 실행에서는 `--data-dir`를 허용하지 않습니다. 자동 테스트는 가짜 어댑터·프로세스 스냅샷·합성 로그와 전용 보조 EXE의 무해한 입력으로 수행하며 PowerSI나 Tcl을 실행하지 않습니다.

## 알려진 한계

저부하는 계산 완료의 증명이 아닙니다. 외부 작업이 라이선스를 기다리지만 상태가 읽히지 않으면 유휴로 오인할 수 있으므로 실제 환경에서 기준을 검증해야 합니다. 스케줄러 시작 이전에 부모 PowerSI가 사라진 외부 고아 solver는 부모 관계를 복원할 수 없습니다. 자체 실행에서 이미 기록한 자식 PID는 재시작 후에도 별도로 확인합니다.

짧은 시뮬레이션의 시작 전이를 놓쳤거나 로그 규칙이 없으면 완료를 자동 승인하지 않습니다. SPD 모드 식별은 UTF-8/BOM 텍스트의 각 줄을 읽으며, 1 MiB를 넘는 단일 줄이나 모호한 규칙은 거부합니다. 대규모 SPD의 첫 규칙 탐색에는 시간이 걸릴 수 있습니다. 로그 판정은 최근 256 KiB를 사용합니다. 지원 모드·인코딩·상태 문구는 별도 PC 검증 결과에 한정됩니다.

현재 설치파일은 코드 서명되지 않았습니다. PowerSI 및 Cadence 설치파일은 포함하지 않으며 Cadence와 독립적인 도구입니다.
